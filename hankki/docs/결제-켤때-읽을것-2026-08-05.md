## 2️⃣ ⭐⭐ 8월에 볼 숫자 — 창업자가 고른 둘

> 창업자 *"② 일주일에 한 번이라도 연 사람 ③ 레꾸를 실제로 저장한 사람 이게 중요하지."*

| | 무엇 | 지금 볼 수 있나 |
|---|---|---|
| ② | 일주일에 한 번이라도 연 사람 | ✅ **Play Console 「통계」** — 활성 사용자·유지율 |
| ③ | **레꾸를 실제로 저장한 사람** | ⛔ **지금은 못 센다** |

### ⛔ ③ 을 못 세는 이유
우리 앱은 **서버가 없다.** 레시피도 꾸미기도 전부 각자 폰 안(localStorage)에 있어 우리에게 안 온다.
개인정보 면에선 깨끗한 구조인데 **대신 아무것도 못 센다.** 분석 도구도 하나도 안 붙어 있다(확인 완료).

### ✅ 언제 셀 수 있나
**재심사 승인 «뒤»에 Firebase Analytics 를 붙인다.** 어차피 결제 켤 때 데이터 보안을 다시 신고해야 하니 **같이** 한다.
⛔ **8/16 전엔 절대 붙이지 않는다** — 데이터 보안 신고가 재심사를 흔든다.
⚠️ 「Analytics 를 붙이면 데이터 보안 신고 대상인가」는 **공식 확인을 아직 안 했다.** 붙이기 전에 확인할 것.

### 📈 붙일 때 보낼 이벤트 (지금 정해둔다 — 그날 헤매지 않게)

| 이벤트 | 왜 |
|---|---|
| `decor_save` | ⭐⭐ **이게 답이다.** 「몇 명이 · 몇 번」 — 유료 판단의 유일한 근거 |
| `decor_open` | 열었는데 저장을 안 했다 = 어렵거나 재미없다 (`decor_save` 와 비교) |
| `recipe_save` | 앱은 쓰는데 꾸미기만 안 하는 건지 |
| `pack_view` / `pack_buy` | 결제 켠 뒤 — 팩 창을 열고 «안 산» 비율 |

⭐ **핵심은 `decor_open` 대비 `decor_save`.** 열었는데 저장을 안 하면 꾸미기가 어려운 것이고,
　 **그건 팩을 파는 것보다 먼저 고칠 문제다.**

### ⭐⭐ 정할 때 반드시 기억할 것

> **컷 수는 나중에 «못 줄인다». 가격은 나중에 «올릴 수 있다».**
