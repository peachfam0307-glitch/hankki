    - 이름 「한끼」. 레시피를 저장하고 표지를 꾸미는 앱. 개인 개발자 1인(비개발자 창업자 + AI).
    - 기술 구조: **PWA(웹앱)를 TWA(Trusted Web Activity)로 감싸서** 구글 플레이에 올림. 안드로이드 전용.
      네이티브 안드로이드 코드는 거의 없고, 실제 화면은 전부 웹(React)입니다.
    - 현재 상태: 비공개 테스트 중, 프로덕션(정식 출시) 액세스 재심사 결과 대기 중.

    - 유일한 서버 = **Cloudflare Workers 하나**. 사진에서 글자를 읽는 OCR 중계용이고,

    - 초기 매출 예상 = 월 수만~수십만 원 수준. 고정비가 월 몇만 원만 나가도 적자입니다.

    【서버가 필요해 보이는 이유 세 가지 — 서로 성격이 다릅니다】
    
    (1) 데이터를 잃습니다
        폰을 바꾸거나 앱을 지웠다 깔면 저장한 레시피가 **전부 사라집니다.**
        태블릿에 깔면 처음 쓰는 것처럼 빈 앱이 됩니다.
        지금은 "백업 파일을 직접 저장하세요" 안내만 있습니다.
        → 오래 쓴 사람일수록 잃을 게 크고, 그게 이탈·악평으로 이어진다고 봅니다.
    
    (2) 영구 상품(꾸미기 팩)을 그냥 팔면 3일 뒤 환불된다고 들었습니다
        구글 문서상 인앱 구매를 "acknowledge(확인)" 하지 않으면 3일 뒤 자동 환불되고 구매가 회수됩니다.
        그런데 우리가 쓰는 **Digital Goods API v2.1 에는 acknowledge() 메서드가 없습니다**
        (v1.0 에만 있었고 삭제됨. 메서드는 getDetails / listPurchases / listPurchaseHistory / consume 넷뿐).
        구글 크롬 문서도 "이 단계는 반드시 백엔드로 구현해야 한다"고 적고 있습니다.
        → 즉 **서버에서 Google Play Developer API 의 purchases.products.acknowledge 를 호출**해야 합니다.
        (소모성 상품은 consume() 이 확인을 겸해서 안 걸린다고 이해했습니다 — 이것도 맞는지 확인 부탁드립니다.)
    
    (3) 「몇 장 남았나」를 폰에만 두면 조작됩니다
        AI 스캔 잔량을 브라우저에 저장하면 유저가 값을 고칠 수 있습니다.
        또 폰을 바꾸면 산 크레딧이 사라집니다.

    【지금 우리가 «잠정적으로» 정해 둔 안 — 이게 맞는지 봐 주세요】
    
    - 클라우드 저장 = **Firebase(Spark 무료 요금제)** + 구글 계정 로그인
      · Firestore 무료: 저장 1GB, 하루 읽기 5만 / 쓰기 2만 / 삭제 2만
      · Authentication 표준 로그인(구글 포함) 무료, 기간 제한 없음
      · **Cloud Storage(사진 창고)는 2026-02-03 부터 카드(Blaze) 필수**라 안 씁니다
      · 그래서 **표지 사진을 Firestore 문서 안에 직접 넣을 생각입니다**
        (문서 한 칸 1MiB 한도 / 우리 표지 사진은 800×800 JPEG ≈ 185KB, 640×640 으로 줄이면 ≈ 64KB)
    - 결제 확인(acknowledge) + 잔량 = **이미 쓰고 있는 Cloudflare Workers 에 얹기**
      · 잔량 저장은 Cloudflare D1(SQLite) 을 생각 중이고, purchaseToken 에 UNIQUE 를 걸어
        같은 영수증으로 두 번 충전되지 않게 하려 합니다.

## ① 제미나이 답 원문 (창업자가 받아옴 · 2026-08-19)

> ⛔ 판정에서 틀린 것으로 확인된 곳: 「Cloudflare = 카드 등록 필수 → 불가」(R2 와 D1 을 뭉갬 · 3 대 1로 뒤집힘)
> · Q8 의 드라이브 추천(지피티 2차가 약관 원문으로 죽임)

현재 앱의 구조와 제약 조건(비용 0원, 카드 등록 불가, 1인 개발)을 고려할 때, 매우 현실적이고 치열한 고민이 담긴 설계입니다. 요청하신 사항에 맞춰 각 질문에 대해 표 형식으로 명확하게 답변해 드립니다.

### Q1. 정말 서버가 필요합니까? (서버 없이 푸는 길)

결론부터 말씀드리면, **결제(영구 상품)와 잔량 위변조 방지를 위해서는 서버(또는 Cloudflare Workers 같은 서버리스 환경)가 반드시 필요**합니다.

| 항목 | 서버 없이(클라이언트만으로) 해결 가능 여부 | 판단 근거 및 현실성 |
| --- | --- | --- |
| **안드로이드 자동 백업 (Auto Backup)** | **불가능** | 안드로이드 Auto Backup은 네이티브 앱의 데이터(SharedPreferences 등)만 백업합니다. TWA는 크롬 브라우저를 띄우는 방식이므로, 크롬의 데이터 폴더에 저장되는 웹 `localStorage`는 백업 대상에서 제외됩니다. |
| **브라우저 계정 동기화** | **불가능** | 크롬 동기화는 북마크, 비밀번호 등을 동기화할 뿐, 일반 웹사이트의 `localStorage`나 `IndexedDB` 데이터를 기기 간에 자동으로 동기화해주지 않습니다. |
| **구글 드라이브 `appDataFolder`** | **가능 (하지만 로그인 필수)** | 사용자 기기(React)에서 Google Identity Services로 OAuth 로그인을 구현하면, 사용자 본인의 드라이브 여유 공간에 숨김 파일로 데이터를 백업할 수 있습니다. **서버와 저장소 비용은 완벽히 0원**입니다. 단, '구글 로그인' 절차가 추가되어야 합니다. |
| **영구 상품 클라이언트 `acknowledge`** | **불가능** | Digital Goods API v2.1은 클라이언트 단의 `acknowledge`를 지원하지 않습니다. 구글 정책상 반드시 서버 투 서버로 `Google Play Developer API`를 호출해 서비스 계정으로 인증 후 확인(Acknowledge)해야 환불을 막을 수 있습니다. 소모성 상품의 `consume()`은 그 자체로 확인을 겸하므로 예외가 맞습니다. |

### Q3. 리스크 분석

| 리스크 항목 | 내용 및 평가 |
| --- | --- |
| **무료 요금제 미사용 정지 여부** | **Firebase:** 일정 기간 미사용 시 프로젝트가 자동 삭제되는 명시적 정책은 없습니다. 단, Cloud Functions 등 일부 기능은 주기적 업데이트가 없으면 Node.js 버전 지원 종료로 막힐 수 있습니다. **Cloudflare:** 무료 계정 미사용 정지 정책은 현재 없습니다. (Supabase는 1주일 미사용 시 DB가 일시 중지되는 것이 맞습니다.) |
| **무료 요금제 혜택 축소 전례** | **존재함.** Heroku의 무료 티어 폐지, Firebase Storage의 Blaze 요금제 강제화(2026-02) 등 클라우드 업계 전반적으로 무료 티어를 축소하는 추세입니다. 의존도를 낮추는 것이 가장 안전합니다. |
| **서비스 집중 vs 분산 리스크** | **1인 개발자에게는 집중이 유리합니다.** Firebase와 Cloudflare로 쪼개면 장애 포인트가 2배가 되고, 두 서비스 간 데이터 정합성을 맞추는 코드(예: 결제는 CF에서, 레시피는 Firebase에서)를 직접 작성하고 유지보수해야 하는 치명적인 부담이 생깁니다. |

### Q4. Cloudflare Workers에서 Google Play API 호출 가능 여부

**가장 중요한 결제 문제: Cloudflare Workers만으로 완벽히 해결 가능합니다.**

| 항목 | 가능 여부 및 구현 방법 |
| --- | --- |
| **서비스 계정 JWT (RS256) 서명** | **가능.** Web Crypto API (`crypto.subtle.sign`)를 사용하여 V8 Isolate 환경에서도 외부 라이브러리 없이 직접 JWT를 생성하고 RS256으로 서명할 수 있습니다. |
| **Google API 클라이언트 없이 fetch 호출** | **가능.** 직접 서명한 JWT를 `https://oauth2.googleapis.com/token`으로 POST 전송하여 Access Token을 발급받은 뒤, 이 토큰을 헤더에 담아 `fetch`로 Play Developer API(`.../acknowledge`)를 호출하면 됩니다. |
| **비밀키 저장의 안전성** | **안전함.** 구글 서비스 계정의 `.json` 키 파일 중 `private_key` 문자열을 Cloudflare Workers의 `Secret` 환경변수로 등록(`wrangler secret put`)하면 코드에 노출되지 않아 안전하게 사용할 수 있습니다. |

### Q5. Firestore 문서 안에 사진(base64) 직접 저장의 실무적 평가

| 항목 | 실무적 평가 및 계산 |
| --- | --- |
| **실제 앱 사례 및 안티패턴 여부** | **명백한 안티패턴입니다.** 문서 기반 NoSQL은 검색과 인덱싱을 위한 곳이며, Base64 문자열을 넣으면 문서 크기가 비대해져 전체적인 성능 저하가 발생합니다. 하지만 1인 개발자의 '비용 0원' 제약 하에서는 합리적인 해킹(Hack)이 될 수 있습니다. |
| **용량 및 비용 제약 계산** | **저장 용량:** 1GB 제한. 1인당 30개 레시피 × 15장 사진(64KB) = 약 1MB. **단순 계산 시 1,000명 저장 가능.** ⭐ **진짜 문제는 대역폭(Egress)입니다:** Firestore 무료 한도는 월 10GB 다운로드입니다. 목록 화면을 그리기 위해 레시피 목록을 불러올 때마다 Base64 사진이 전부 다운로드됩니다. 100명이 하루 1번씩만 전체 목록(1MB)을 조회해도 한 달이면 3GB가 소모됩니다. 유저가 조금만 늘어도 한도가 먼저 막힙니다. |
| **해결책 (구조 개선)** | Base64를 쓰더라도 **반드시 컬렉션을 분리해야 합니다.** `recipes` 컬렉션에는 텍스트(제목, 날짜)만 두고, 사진 데이터는 `recipe_images`라는 별도 컬렉션(또는 하위 컬렉션)에 저장하여, 상세 화면에 들어갈 때만 사진 문서를 불러오게(`fetch`) 설계해야 대역폭 고갈을 막을 수 있습니다. |

### Q1. 정말 서버가 필요한가? — **결론: 필요하다 (단, "서버 운영"이 아니라 이미 있는 Workers 확장 수준)**

| 서버 없이 푸는 후보 | 되나? | 근거 |
|---|---|---|
| Android Auto Backup으로 TWA localStorage 복원 | **안 됨** 🟡 | TWA의 웹 데이터는 앱 자신의 데이터 폴더가 아니라 **Chrome 브라우저의 프로필 안**에 삽니다. 실제로 유저가 Chrome의 방문 기록/브라우징 데이터를 지우면 앱 상태까지 초기화된다는 것이 5만 설치 규모 TWA 개발자의 보고입니다. Auto Backup은 앱 자신의 데이터만 백업하므로 Chrome 프로필 속 사이트 데이터는 대상이 아닙니다. |
| Chrome 계정 동기화로 localStorage 기기 간 이동 | **안 됨** 🟡 | Chrome 동기화 대상은 북마크·비밀번호·기록·설정 등이고 **사이트 데이터(localStorage/IndexedDB)는 동기화 항목이 아닙니다.** (표준 지식 수준의 확신이지만 오늘 별도 출처 확인은 안 했음) |
| 구글 드라이브 appDataFolder에 직접 저장 | **기술적으로 가능하지만 ToS 지뢰** ✅ | 기술 자체는 됩니다(drive.appdata 스코프로 앱 전용 숨김 폴더 접근, 만든 앱만 읽을 수 있고 Drive UI에는 안 보임). 그런데 결정적으로, 구글 드라이브 API 약관이 "개발자 앱 콘텐츠의 Drive 백업"을 구글의 사전 서면 동의 없이는 허용하지 않는 제한 용도로 명시하고 있습니다. 소규모 앱들이 실제로 많이 쓰고 있고 제재 사례는 못 찾았지만(❓), 약관 문면상 리스크가 있는 건 사실입니다. 추가로 웹 전용 OAuth는 브라우저에서 refresh token을 못 받아 액세스 토큰이 1시간짜리라 재동의 UX가 번거롭습니다(🟡). |
| 영구 상품 acknowledge를 클라이언트만으로 | **불가능** ✅ | 문서에 쓴 이해가 정확합니다. DGAPI 2.0부터 acknowledge는 백엔드에서 Google Play Developer API로 해야 하고, 클라이언트의 acknowledge() 호출은 전부 제거하라는 것이 공식 마이그레이션 가이드입니다. 3일 내 확인하지 않으면 자동 환불 + 구매 회수도 공식 문서 그대로입니다. |
| 소모성은 consume()으로 통과? | **맞음** ✅ | consume이 acknowledge 요건을 겸하며, 백엔드가 없는 클라이언트 전용 앱은 클라이언트 consume을 쓰라고 공식 문서가 명시합니다. 다만 백엔드가 있다면 서버 쪽 Purchases.products:consume을 권장하니, 어차피 Workers를 만들면 소모성도 서버에서 처리하는 게 낫습니다(잔량 조작 방지와도 맞물림). |

**정리**: 세 이유 중 (2)acknowledge와 (3)잔량은 서버 없이 못 풉니다. (1)백업만이라면 Firebase 같은 BaaS로 "직접 운영하는 서버 없이" 해결 가능. 잠정안의 방향(Firebase + Workers 분담)은 타당합니다.

### Q4. Workers에서 Google Play Developer API 호출 — **됩니다** ✅

| 질문 | 답 |
|---|---|
| V8 isolate에서 RS256 서명 가능? | **가능.** Workers는 Node 내장 crypto를 지원하지 않지만 Web 표준인 crypto.subtle을 지원하며, 구글 공식 SDK(googleapis)는 Node 의존이라 못 쓰는 대신 JWT를 직접 만들어 서명 → OAuth 엔드포인트에서 액세스 토큰 교환하는 방식으로 인증합니다. |
| 실제 사례 | 여럿. 서비스 계정 JSON의 PEM 개인키를 SubtleCrypto로 다뤄 JWT를 서명하고, OAuth 토큰이 필요하면 aud를 oauth2.googleapis.com/token으로 두고 scope를 넣어 교환하는 방법을 단계별로 다룬 가이드가 있고, WebCrypto로 JWT를 만들어 주는 워커 전용 라이브러리(@sagi.io/workers-jwt)가 GCP 서비스 계정 헬퍼까지 내장하고 실서비스에서 쓰이고 있으며, `jose` 라이브러리의 importPKCS8 + SignJWT 조합 사례도 있습니다. |
| 라이브러리 없이 fetch만으로? | 가능 — 위 방식이 바로 그것(JWT 생성 → `fetch`로 토큰 교환 → `fetch`로 `purchases.products.acknowledge` 호출). scope는 `https://www.googleapis.com/auth/androidpublisher` 🟡. |
| 비밀키를 Workers Secret에? | 표준 관행입니다. 서비스 계정 JSON 키를 Worker secret으로 저장해 환경변수로 안전하게 쓰는 방식이 가이드에도 그대로 나옵니다. 대안으로 wrangler secret에 키 문자열만 넣고 코드에서 조립. |

즉 "꾸미기 팩을 영영 못 판다"는 시나리오는 걱정 안 해도 됩니다. 서비스 계정에 Play Console의 API 액세스 권한을 연결하는 설정 작업은 별도로 필요합니다(🟡).

### Q5. Firestore 문서에 사진(base64) — **되긴 되는데, 조건부**

| 쟁점 | 판단 |
|---|---|
| 1MiB 외의 문제 | ① base64는 원본보다 **약 33% 커짐**(185KB → 약 247KB 문서) 🟡 ② 목록 화면에서 문서를 읽으면 **사진까지 통째로 딸려 옴** → 읽기 횟수보다 **월 10GiB 송신 한도**가 먼저 문제가 됨 ③ 사진 필드에 인덱스가 걸리지 않게 제외 설정 필요 ④ 첫 로딩이 느려짐. 해법: **사진을 별도 서브컬렉션 문서로 분리**해서 목록은 텍스트만 읽고 상세에서만 사진 문서를 읽게 하면 대부분 해소됩니다. |
| 1GB에 몇 명? (레시피 30편 중 15편 사진) | base64 팽창 반영 시: 800px(185KB→247KB)이면 유저당 ≈3.7MB → **약 280명**. 640px(64KB→85KB)이면 유저당 ≈1.3MB → **약 800명**. (텍스트·인덱스 오버헤드 제외한 내 계산이므로 ±로 보세요.) 초기 수십~수백 명 목표에는 640px 기준으로 충분. |
| 실제 사례 vs 안티패턴 | 교과서적으로는 안티패턴으로 분류됩니다(원래 정답이 Cloud Storage였으니까). 다만 그 정답이 2026-02-03부터 카드 필수가 된 지금, **작은 이미지 한정 + 문서 분리 + 강한 압축** 조건이면 합리적 차선입니다. 이 구조를 쓰는 유명 앱 사례는 못 찾았습니다 ❓. |

### Q6. 한국 개인정보보호법 국외 이전 — **처리방침 공개로 갈음 가능, 근거 조문도 맞음** ✅

### Q7. 구글 플레이 계정 삭제 요건 — **앱 내 경로 + 웹 링크 둘 다 필수** ✅

### Q1. 서버가 정말 필요한가?

| 문제 | 서버 필요성 | 판단 |
| --- | ---: | --- |

| 영구 스티커 구매 승인 | 필수 | 현재 Digital Goods API에서는 클라이언트만으로 안전한 승인을 완결하기 어려움 |
| AI 스캔 잔량·중복 구매 방지 | 필수 | 클라이언트 저장값은 조작 가능하고, 소모된 구매는 기기 변경 시 복구할 원장이 필요 |

| 사진 저장 | 선택적 | 초기에는 IndexedDB+Drive 백업으로 충분 |

**현재 데이터는 자동 복구되지 않습니다** — TWA의 웹 콘텐츠는 Chrome이 렌더링하며, Android 래퍼 앱은 웹의 쿠키·`localStorage` 같은 상태에 직접 접근하지 못합니다. 따라서 Android Auto Backup이 래퍼 APK를 백업하더라도 Chrome의 사이트 저장소까지 복구해 준다고 기대할 수 없습니다. Chrome 동기화 목록에도 사이트별 `localStorage`나 IndexedDB 동기화는 포함되지 않습니다. 따라서 지금 구조에서는 **앱 삭제, Chrome 데이터 삭제, 기기 고장**으로 데이터가 사라질 수 있습니다.

**Google Drive만으로 백업할 수 있는가?** — 가능합니다(⛔2차에서 약관 확인 후 철회). `appDataFolder`는 사용자 Drive 안의 앱 전용 숨김 폴더이며 REST API로 직접 접근할 수 있습니다. 데이터 용량도 개발자 계정이 아니라 사용자 Drive 할당량에 포함됩니다. 다만 사용자가 앱 데이터를 직접 삭제하거나 접근 권한을 철회할 수 있습니다. 브라우저에서 Google Identity Services 토큰 모델로 Drive REST API를 직접 호출할 수 있으므로 별도 서버에 refresh token을 보관하지 않아도 됩니다. 단, access token 갱신에는 보통 사용자 동작이 필요하므로 완전한 무인 백그라운드 동기화보다는 "지금 백업/복원" 또는 로그인 세션 동안의 자동 백업에 적합합니다. 중요하게도 Drive 파일은 사용자가 수정·삭제할 수 있으므로 **결제 잔량 원장으로는 사용하면 안 됩니다.**

**결제 백엔드는 왜 필요한가?** — Google Play 구매는 3일 안에 승인되지 않으면 환불·회수될 수 있습니다. PWA/TWA의 Digital Goods API 흐름은 구매 토큰을 백엔드에서 Play Developer API로 검증·승인하는 구조를 안내합니다. AI 스캔 잔량을 `localStorage`나 Drive에 두면 사용자가 값을 조작하거나 예전 백업으로 되돌릴 수 있습니다. 따라서 `purchaseToken`의 중복 사용 여부와 현재 잔량은 D1을 권위 있는 원장으로 삼아야 합니다.

### Q5. Firestore 문서에 사진을 직접 넣어도 되는가?

기술적으로는 가능하지만 레시피 문서 안에 Base64 사진을 함께 넣는 방식은 장기적으로 피해야 합니다.

| 사진 크기 | 저장 방식 | 1인당 사진 용량 | 1GiB 이론상 사용자 수 |
| ---: | --- | ---: | ---: |
| 185KB | Firestore Bytes | 2.775MB | 약 387명 |
| 185KB | Base64 문자열 | 약 3.70MB | 약 290명 |
| 64KB | Firestore Bytes | 0.96MB | 약 1,118명 |
| 64KB | Base64 문자열 | 약 1.28MB | 약 839명 |

운영 여유 15~25%를 잡으면 현실적 상한: 185KB Base64 약 220~250명 · 64KB Base64 약 650~710명. 불가피하게 저장한다면: Base64 대신 `Bytes` / 텍스트 문서와 사진 문서 분리 / 사진 필드 인덱스 제외 / 목록은 썸네일만 lazy load / 640×640, 64KB 전후 파일 사용. "Firestore 문서에 대량 Base64 사진을 장기간 운영한 모범 사례"는 확인하지 못했습니다.

### 1. 백업 금지 조항과 `appDataFolder`

현재 공식 Google Drive API 이용약관(developers.google.com/workspace/drive/api/terms)에는 다음 문구가 그대로 있습니다.

> "Backup of user or app content from a developer's app or project to Drive."

즉, 개발자 앱·프로젝트의 사용자 콘텐츠나 앱 콘텐츠를 Drive에 백업하는 용도는 **Google의 사전 명시적 서면 동의 없이 허용되지 않습니다.**

공식 페이지에는 약관 최종 수정 2022-07-08 · 문서 페이지 최종 업데이트 2026-07-22 · 확인일 2026-08-19 로 표시되므로 현재도 유효한 조항으로 봐야 합니다.

**`appDataFolder`는 예외인가?** — 명시적인 예외가 아닙니다.

| 사용 내용 | 판단 |
| --- | --- |
| 테마 설정, 마지막 동기화 시각, 앱 환경설정 | `appDataFolder`의 명시적 용도에 가까움 |
| 캐시 인덱스, 동기화 커서, 작은 내부 상태 | 대체로 적합 |
| 사용자가 만든 레시피·일기·사진 전체 복사본 | 약관상 "user or app content backup"에 해당할 가능성이 매우 높음 |
| 앱 삭제·기기 변경에 대비한 복원 파일 | 목적 자체가 백업이므로 금지 조항에 직접 걸림 |
| Drive를 앱의 주 데이터베이스로 사용 | 백업과 동일하지는 않지만 경계가 불명확해 Google 서면 확인 없이 권장하기 어려움 |

`appDataFolder`가 기술적으로 파일 업로드를 허용한다고 해서, 그 안에 무엇이든 백업해도 된다는 뜻은 아닙니다. **기능 문서와 사용목적 제한 약관이 동시에 적용됩니다.** 따라서 HANKKI의 레시피·사진 전체를 `appDataFolder`에 백업하는 설계는 철회하는 것이 안전합니다.

참고로 약관의 "제한된 Drive scope를 허용하는 사례"에 나오는 자동 백업은 **앱 데이터를 Drive로 백업하는 것**이 아니라, 사용자의 기존 Drive 파일을 로컬로 동기화·백업하는 앱을 주로 가리킵니다. 이 문장을 HANKKI 백업 허용 근거로 해석하면 안 됩니다.

**약관에 걸리지 않는 대안**
* 사용자가 HANKKI에서 ZIP/JSON 파일을 직접 다운로드
* 사용자가 그 파일을 원하는 곳이나 자신의 Drive에 수동 업로드
* 앱은 Drive API를 전혀 호출하지 않음

이 방식은 HANKKI가 Drive API를 백업 서비스로 사용하는 것이 아니므로 가장 안전합니다. Drive 자동 백업을 꼭 쓰려면 Google로부터 **사전 명시적 서면 동의**를 받아야 합니다.

### 2. 브라우저 OAuth와 refresh token

**순수 브라우저 방식** — Google Identity Services의 브라우저용 Token Model은 **refresh token을 발급하지 않습니다.** 브라우저가 받는 것은 수명이 짧은 access token입니다. 만료되면 `requestAccessToken()`을 다시 호출해야 하며, 현재 공식 문서는 이 호출을 버튼 클릭 같은 사용자 동작에서 실행하라고 요구합니다. 이전 동의는 기억되므로 매번 전체 동의 화면이 나오지는 않을 수 있지만, 완전한 무인 자동 갱신은 아닙니다. 앱을 닫아 둔 상태에서 계속 자동 백업하는 구조는 만들 수 없습니다.

**refresh token을 받는 방법** — Authorization Code 방식에서 `offline` 접근으로 받아야 합니다. 웹앱의 authorization code를 **백엔드에서 access token·refresh token으로 교환하고, refresh token을 안전하게 저장**하도록 안내합니다. HANKKI라면 기존 Cloudflare Worker를 사용할 수 있습니다. 권장 보관: refresh token을 브라우저에 돌려주지 않기 / Worker Secret을 암호화 키로 / 암호화한 값만 D1에 저장 / 사용자별 최소 식별자와 연결 / 계정 삭제 시 token 폐기·Google 권한 revoke / 로그에 code·access token·refresh token을 남기지 않기. 이것은 물리 서버를 직접 운영하는 것은 아니지만, 엄밀히 말하면 **서버 없는 방식은 아니고 serverless backend 방식**입니다.

**브라우저에 refresh token을 저장하면?** — 권장하지 않습니다. GIS Token Model 자체가 브라우저에 refresh token을 주지 않고, refresh token은 장기간 사용자 Drive에 접근할 수 있는 비밀정보이며, `localStorage`·IndexedDB에 넣으면 XSS나 악성 스크립트에 탈취될 수 있고, Web OAuth client secret도 브라우저 코드에 숨길 수 없습니다.

**테스트 상태 주의** — OAuth 동의 화면이 `Testing` 상태이고 Drive 같은 추가 scope를 요청하면 테스트 사용자의 권한과 refresh token은 **7일 후 만료**됩니다. 실제 서비스에서는 OAuth 앱을 `In production`으로 전환해야 합니다. 사용자가 권한을 철회하거나 Google의 보안 정책으로 무효화되는 경우에는 production 상태에서도 refresh token이 언제든 무효가 될 수 있습니다. 앱은 재연결 절차를 반드시 제공해야 합니다.

### HANKKI에 대한 수정 결론
* `appDataFolder` 전체 백업: **사용하지 않는 것이 맞음**
* 순수 브라우저 지속 자동 Drive 쓰기: **불가능**
* 버튼을 누를 때마다 브라우저 access token으로 쓰기: 기술적으로 가능하지만 **백업 약관 문제는 그대로**
* Worker에 refresh token을 보관하는 자동화: 기술적으로 가능하지만 **Google의 백업 서면 동의가 먼저**
* 현재 가장 안전한 무과금 방식: **IndexedDB + ZIP/JSON 내보내기·가져오기**
* 자동 클라우드 복원이 필요하면: Drive가 아니라 Firestore 등 **해당 용도가 허용된 저장 서비스**를 검토해야 함
