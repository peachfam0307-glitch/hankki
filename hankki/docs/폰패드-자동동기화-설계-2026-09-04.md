# ☁️🔄 폰↔패드 자동 동기화 — 설계 (2026-09-04) ⭐현행

> 📮 창업자 = *"폰에서 꾸민 것들, 추가한 것들 패드에 반영이 안되고 있어(자동으로)"*
> → *"ⓑ로 가자. 설계부터 제대로 해줘"* → *"다각도로 리스크고려해서 검토해봐 구멍이 있을 수도 있잖아"*
> → *"한번만 더 흔들어봐"* → *"다른 앱들은 어떻게 동기화 하는지 좀 파봐"*
> → *"시작하자 **이건 네가 우리앱을 책임지는거야** 이거 잘못되면 답이 없어"*

⛔⛔ **이 문서는 「만들기 전에 다섯 번 흔든 기록」이다.** 구현하다 막히면 여기부터 다시 읽는다.

## 0. 지금 상태 (실측 · 2026-09-04)

| | 상태 | 근거 |
|---|---|---|
| 자동 **올리기** | ✅ 돈다 (앱 켤 때 한 번) | `App.jsx` `저절로올리기` |
| 자동 **받기** | ⛔ **`if (false)` 로 잠겨 있다** | `App.jsx` 「2026-09-01 23:51 · 즉시 껐다」 |
| 받기 방식 | **통째로 덮어쓰기** | `내려받기()` 가 판 전체를 돌려준다 |
| 안전장치 | `안올린변경있나` **하나** | `cloud.js:652` |

⛔ **9/1 사고** = 자동 받기가 «방금 담은 레시피»를 덮었다. 열쇠는 깎였는데 물건이 없었다.
　 **원인은 아직 확정 못 했다.** ⭐그래서 이 설계는 **원인을 몰라도 그 사고가 «날 수 없게»** 만든다(절대원칙 34).

## 1. 뿌리 — 왜 지금 구조가 위험한가

**받기가 「덮어쓰기」다.** 그래서 안전장치 하나가 뚫리면 **바로 데이터가 사라진다.**
✅ 그 모양을 바꾼다 = **덮지 않고 «합친다».** 받기가 «지우는 일»을 아예 못 하게 만든다.

📌 최악이 「사라짐」 → **「지운 게 좀 남아 있음」**으로 내려간다.

## 2. 다섯 번 흔들어 나온 구멍 스무 개

### 1차 · 데이터 모양 (내가 처음 놓친 것)
- **①** 「나중에 고친 것이 이긴다」인데 **`고친때`가 없다**(`savedAt`＝처음 담은 때뿐)
- **②** 합칠 수 있는 건 `recipes`·`diary` 뿐 — **장보기·냉장고·폴더·프로필은 `meta` 문서 «하나»에 통째로**
- **③** 무덤(지웠다 표시)이 없으면 **지운 게 되살아난다**
- **④** 사진 되돌리기가 한 곳 → 편마다로 흩어진다

### 2차 · 사고를 일으켜 보기
- **⑤** 무덤을 **폰에만** 두면 못 막는다 → **클라우드에도 올려야** 한다(＝데이터 모양은 결국 바뀐다)
- **⑥** 「모름끼리 둘 다 남긴다」는 중복을 만든다 → **id 가 같으면 한 편이다**
- **⑦** 받는 중에 꺼지면 반만 들어간다 → **한 번에 얹거나 아예 안 얹거나**

### 3차 · 규모·시간 (절대원칙 32)
- **⑧** `내려받기` 가 **컬렉션 통째로** 읽는다 → 자동이 되면 **켤 때마다 전부**
  🔢 레시피 1000편 × 유저 1만 = **하루 천만 건 읽기** → ⭐**「그때 이후 바뀐 것만」 읽어야 한다**
- **⑨** 무덤이 영원히 쌓인다 → **90일 청소**

### 4차 · 돈·법·이미 깔린 폰
- **⑩** **쓰기도** 유저 수만큼 는다(⑧은 읽기만 봤다) → 켤 때 «한 번»을 지킨다
- **⑪** **계기판이 없다** — OCR 엔 있는데(`?quota=1`) 클라우드엔 없다. 터지고 나서 안다
- **⑫** `hankki:cloud:pulled` 표식이 **폰 안에만** → 브라우저가 비우면 **자동 올리기가 조용히 영영 멈춘다**(지금도 있는 구멍)
- **⑬** 잠긴 일기는 **비번이 기기마다** → 받아도 못 여는 일기가 섞인다

### 5차 · 창업자가 짚어준 각도 (⭐내가 네 번 흔들고도 못 본 것)
- **⑭** **기기 번호(`hankki:did`)가 폰·패드가 다르다 → 열쇠가 두 벌**. 우리 비용 2배 ＋ 유료 전환 때 「산 열쇠가 없다」
  📮 창업자 확정 = **「맞춰야 한다」** ⛔단 서버 일이라 **이 설계와 별개 갈래**로 뺀다
- **⑮** 잠긴 일기는 **합치기에서 제외** ＋ 「이 기기에서 못 여는 일기」를 **정직하게 표시**(빈 칸이면 「사라졌다」로 읽힌다)
- **⑯** SNS 편은 우리 기본 레시피라 동기화 대상이 아니다 ✅ (꾸미는 순간 「내 레시피」가 되어 합치기 대상이 된다)
- **⑰** **기본 레시피는 동기화가 건드리지 않는다** — 안 그러면 `BASICS_VERSION` 으로 바꾼 그림이 한쪽에서 옛것으로 되돌아간다

### 6차 · 남들은 어떻게 하나 (조사)
- **⑱** **칸별로 판정해야 한다** — 「편 통째로」면 폰에서 꾸미고 패드에서 재료 고칠 때 **한쪽이 통째로 날아간다**
- **⑲** **보낼 것 줄서기(outbox)가 없다** — 실패하면 다음에 앱 켤 때까지 그냥 없다
- **⑳** **무덤이 성능을 잡아먹는다**(업계가 치른 값) → ⑨의 90일 청소가 맞는 판단이었다는 근거

## 3. 확정한 설계

### ⓐ 합치기 (덮지 않는다)
| 무엇 | 어떻게 맞추나 |
|---|---|
| 레시피 · 일기 | **`id`** |
| 장보기 · 냉장고 · 위시리스트 | **`name`** (앱이 이미 그 잣대를 쓴다 — `store.jsx` 중복 검사) |
| 폴더 · 프로필 | 통째로 (쪼갤 게 없다) |
| **기본 레시피(우리 것)** | ⛔**안 건드린다**(⑰) |
| **잠긴 일기** | ⛔**합치기 제외**(⑮) |

· 같은 `id` 면 **나중에 고친 것**이 이긴다 · 시각은 **서버 것**을 쓴다(폰 시계는 못 믿는다)
· **칸별 판정**(⑱) — 꾸미기(`decor`)와 본문은 따로 본다
· `고친때` 가 **없는 옛 데이터**끼리 부딪히면 ⛔둘 다 남기지 않는다(⑥) — id 가 같으면 한 편이다

### ⓑ 꼬여도 살아남는 장치 셋 (⭐이게 먼저다)
1. **되돌리기** — 얹기 «직전» 상태를 한 벌 뜬다
   · **글자만**(사진·꾸민 표지 제외 — 둘 다 폰에 그대로 있다)
   · **큰 창고(IndexedDB)에** 둔다 ⛔작은 서랍(localStorage)에 두면 **9/2 사고 재현**
   · **3벌** 보관 · 🔢 실측 = 레시피 한 편 **808 B** · 255편 ≈ **0.2MB** · 3벌 ≈ **0.6MB** (창고 10GB 의 0.006%)
   · 한 벌이 **5MB 를 넘으면 안 만들고 «알린다»** ⛔말없이 실패하지 않는다
2. **동기화 기록** — 「언제 · 무엇이 · 몇 개」 남긴다. ⛔지금은 기록이 0이라 9/1 원인을 못 찾았다
3. **지우는 일은 자동으로 안 한다** — 지울 게 생기면 모아뒀다 **물어본다**. 합치기는 늘 «더하기»만

### ⓒ 계기판 (⑪ · 창업자가 2026-08-31 에 이미 지시한 것)
· 폰 창고 몇 % · 클라우드 저장 몇 % · 이번 달 읽기/쓰기 몇 건
· 🔢 표지 한 장 **368KB** → 100장이면 36MB · 파이어스토어 무료 저장 1GB ≈ **한 사람 2,700장**

### ⓓ 켜는 방식 — 단계로 ✅**창업자 확정 2026-09-04**
📮 창업자 = *"좋아 내 폰-패드로 실험하고 유저꺼로 뿌리는거 확정해도 되니까"*
⛔ 그러니 **창업자 기기 왕복이 끝나기 «전»에는 전체 공개하지 않는다.** 이건 확정이다.
1. **창업자 기기 둘에서만** 켠다(운영자 표식 — 이미 있는 장치)
2. 며칠 실제로 쓰고 **동기화 기록**을 본다
3. 이상 없으면 **전체 공개**
⭐ 클라우드 로그인을 이 방식으로 켰다(2026-08-31) — **같은 길을 그대로 쓴다**

## 4. 만드는 순서 (⛔이 순서를 바꾸지 않는다)

| | 무엇 | 왜 이 순서인가 |
|---|---|---|
| 1 | **재현판** — 합치기·무덤·되돌리기·장보기·사진 | ⛔판 없이 만들면 창업자 폰에서 발견된다 |
| 2 | **되돌리기** ＋ 동기화 기록 | 꼬여도 되돌아갈 수 있어야 그다음을 만진다 |
| 3 | 합치기 ＋ 클라우드 무덤 ＋ 한 번에 얹기 | |
| 4 | 「바뀐 것만 읽기」 ＋ 계기판 | ⑧⑩⑪ — **켜기 «전»에** 해야 한다 |
| 5 | ⛔**그때 `if (false)` 를 푼다** | 판이 «전부» 초록불일 때만 |
| 6 | 창업자 폰·패드 실물 왕복 | |
| 7 | 배포 | ⛔6이 끝난 뒤에만 |

## 5. 정직하게 남기는 것

- ⚠️ **같은 편을 양쪽에서 고치면** 나중 것이 이긴다 — 앞선 수정은 사라진다. 어떤 설계로도 완전히는 못 없앤다
- ⚠️ **9/1 사고의 정확한 원인은 여전히 모른다** — 다만 덮어쓰기가 없어져 **그 길 자체가 사라진다**
- ⚠️ **장보기·냉장고는 창업자가 겪었는지 확인 못 했다**(*"장보기는 잘 모르겠어"*) — 그래도 합치기에 넣는다.
  안 넣으면 자동 받기를 켜는 순간 **거기서 잃을 수 있다**
- ⚠️ **열쇠 맞추기(⑭)는 이 설계 밖**이다 — 서버 일이고 수익과 엮인다. 따로 설계한다
- ⚠️ **로그인 안 한 사람**은 동기화 자체가 없다(계정이 없으니 붙을 데가 없다)

## 6. 왜 CRDT 가 아닌가 (조사 근거)

· CRDT = **여럿이 같은 문서를 동시에** 고칠 때 쓴다(피그마·리니어). 무겁고 데이터가 커진다
· 우리 = **한 사람이 기기 둘**. 동시에 같은 편을 고치는 일이 드물다
· 조사 원문 = *"CRDT 는 협업이 정당화될 때만 써라. 단순 CRUD 에 복잡성을 들이지 마라"*
→ **「나중 것이 이긴다(LWW) ＋ 무덤 ＋ 합치기」가 우리 상황의 표준**이다
