### 답 ① (ChatGPT) — §16.3 의 성격부터 가른 답

> 결론부터 말하면, YouTube API 서비스 약관 §16.3만을 근거로 "사용자가 YouTube 웹 화면에서 직접 복사한 자막 텍스트를 앱에서 이용하면 금지된다"고 보기는 어렵습니다. 다만 그렇다고 자유롭게 쓸 수 있다는 뜻은 아닙니다. 일반 YouTube 이용약관이 별도로 걸릴 수 있습니다.
>
> **1. §16.3의 정확한 성격**
>
> 현재 YouTube API Services Terms of Service §16 제목 자체가 "No Implied Rights", §16.3은 "No Licenses or Rights to Patents or Content"입니다. 즉 엄밀히 말하면 독립적인 "복제 금지 조항"이라기보다는 API 약관으로는 콘텐츠 복제·배포 권리를 주지 않는다는 라이선스 부인 조항입니다.
>
> 공식 영문 핵심 문구는 다음과 같습니다.
> "no rights or licenses are granted to reproduce or distribute audiovisual content or make audiovisual content available in any manner other than through…"
>
> 그리고 마지막에는 명시적으로 부여하지 않은 모든 권리를 YouTube가 유보한다고 규정합니다.
> 한국/APAC 공식 페이지도 동일하게 §16.3에서 "YouTube API 서비스를 사용하는 것이 아닌 다른 방식으로 시청각 콘텐츠를 복제 또는 배포"할 권리를 부여하지 않는다고 되어 있습니다.
>
> **2. 그런데 "자막 텍스트"가 §16.3의 audiovisual content인가?**
>
> 여기가 중요합니다. 약관 문언상 동일하다고 단정하기 어렵습니다.
> 같은 API 약관 §19.5는 API Data의 콘텐츠 종류를 열거하면서 영상(video), 오디오(audio), 그래픽, 사진, text, 인터랙티브 기능, 소프트웨어 등을 서로 별도로 나열하고, 텍스트 예로 comments와 scripts까지 언급합니다.
> 즉 약관 자체가 대략 다음처럼 구분하고 있습니다. text ≠ audiovisual content
>
> 따라서 사람이 웹페이지에서 보고 직접 선택·복사한 자막의 문자 텍스트 그 자체를 §16.3의 "audiovisual content"라고 자동으로 간주한다는 문구는 제가 확인한 공식 약관에는 없습니다.
> 더구나 API 서비스 약관은 애초에 YouTube API Services에 접근하거나 사용하는 경우 적용되는 계약이고, API Data는 API 서비스를 통해 API Client에 제공되는 데이터·콘텐츠를 말합니다. 일반 youtube.com 웹페이지에서 사용자가 직접 복사한 텍스트는 그 행위만 놓고 보면 API를 통해 취득한 API Data가 아닙니다.
>
> **3. 그렇지만 일반 YouTube 이용약관은 별개입니다**
>
> 한국에 제공되는 YouTube 일반 이용약관은 YouTube의 Content를 정의하면서 동영상·오디오뿐 아니라 "text (such as comments and scripts)"도 명시적으로 포함합니다. 즉 자막이나 스크립트 형태의 문자 콘텐츠는 §16.3과 별개로 일반 약관의 Content에 들어갈 가능성이 훨씬 높습니다.
> 그리고 일반 이용약관의 Restrictions는 Content에 대해 "access, reproduce, download, distribute … alter, modify or otherwise use"하는 것을 제한하고, 서비스에서 명시적으로 허용하거나 권리자로부터 허가받은 경우 등을 예외로 둡니다.
> 따라서 웹 UI에서 사람이 직접 복사했기 때문에 API §16.3을 피했다고 하더라도, 일반 YouTube 이용약관 문제는 별도로 남습니다.
>
> **4. "원문 그대로 게시하지 않고 재작성"하면?**
>
> API §16.3만 보면: 사용자가 웹 화면에서 가져온 텍스트를 대상으로 하는 조항이라고 명시돼 있지 않으므로, 재작성 여부보다 애초에 §16.3의 직접 적용 대상인지가 불명확/낮습니다.
> 반면 일반 YouTube 이용약관은 단순 복제뿐 아니라 alter, modify, otherwise use도 문언에 포함합니다. 따라서 「자막 원문 복사 → AI가 문장만 바꿈 → 앱에 게시」라는 이유 하나만으로 YouTube 이용약관상 확실히 허용된다고 말할 수는 없습니다.
> 다만 저작권 문제는 또 별개입니다. 예를 들어 자막에서 "양파 1개, 간장 2큰술, 10분 볶는다" 같은 사실·조리 정보만 추출하여 독립적인 문장·구조로 새 레시피를 작성하는 것과, 자막의 문장·설명·구성을 사실상 그대로 옮겨 표현만 조금 바꾸는 것은 법적으로 같은 상황이 아닙니다.
>
> | 상황 | API 약관 §16.3 |
> |---|---|
> | Caption API 등으로 자막/콘텐츠를 취득 | API 약관 직접 관련 |
> | YouTube 영상 자체를 복제·배포 | §16.3이 명확히 문제됨 |
> | 사용자가 YouTube 웹 화면에서 자막을 직접 복사 | §16.3이 이를 직접 금지한다고 명시돼 있지 않음 |
> | 그 자막을 그대로 앱에 게시 | §16.3보다 일반 YouTube 약관 + 저작권 검토가 중요 |
> | 자막에서 정보만 추출해 완전히 새 문장으로 작성 | §16.3의 audiovisual-content 조항과는 거리가 더 멂, 하지만 일반 약관·저작권 문제까지 자동 해결되는 것은 아님 |
>
> 따라서 "§16.3 때문에 사용자가 수동 복사한 자막을 바탕으로 레시피를 재작성하는 것까지 금지된다"라고 해석하는 것은 약관 문언보다 넓은 해석입니다. 반대로 "재작성만 하면 YouTube 약관상 무조건 허용된다"고 말하는 것도 어렵습니다. 핵심 쟁점은 §16.3보다는 일반 YouTube 이용약관의 Content 사용 제한 쪽입니다.

### 답 ② (Perplexity) — 스크래핑 조항 쪽을 짚은 답

> 결론부터 말하면, **§16.3만으로 자막 텍스트 전체가 항상 '시청각 콘텐츠'에 포함된다고 단정하기는 어렵습니다.** 다만 자막은 YouTube API가 제공하는 **텍스트·스크립트 등 API Data**일 수 있고, 이를 대량으로 복사·저장·게시하는 행위는 §16.3뿐 아니라 개발자 정책의 스크래핑·데이터 보관·제3자 권리 조항에 걸릴 위험이 큽니다. 원문을 재작성하더라도 안전하다고 자동으로 보장되지는 않습니다.
>
> **조항 원문**
> > **16.3 No Licenses or Rights to Patents or Content.** Without limiting the generality of the foregoing, no rights or licenses are granted under any patents owned or controlled by YouTube or its Affiliates, and no rights or licenses are granted to reproduce or distribute audiovisual content or make audiovisual content available in any manner other than through the use of the YouTube API Services in accordance with the Agreement. All rights not expressly granted to you are reserved by YouTube.
>
> 같은 약관은 API Data에 동영상과 오디오뿐 아니라 **"text"와 "scripts"**도 포함될 수 있다고 명시합니다.
> > **API Data Content.** THE CONTENT PROVIDED AS PART OF API DATA INCLUDES VIDEOS, AUDIO, GRAPHICS, PHOTOS, TEXT, INTERACTIVE FEATURES, SOFTWARE, AND OTHER MATERIALS, INCLUDING MUSIC, SOUNDS, COMMENTS, SCRIPTS, AND AUDIOVISUAL COMBINATIONS.
>
> **웹 화면에서 직접 복사한 경우**
>
> 질문처럼 **API가 아니라 YouTube 웹 화면에서 자막을 직접 복사**했다면, 엄밀히는 §16.3의 "YouTube API Services를 통해 제공되는 콘텐츠"라는 문구가 직접 적용되는지는 별도 문제입니다. 그러나 그것이 허용된다는 뜻은 아닙니다.
> 개발자 정책은 다음과 같이 규정합니다.
> - YouTube 애플리케이션 또는 Google 애플리케이션을 직접·간접적으로 스크랩하거나, 스크랩된 YouTube 데이터·콘텐츠를 얻어서는 안 됩니다.
> - 공공 검색엔진의 예외는 YouTube의 `robots.txt` 또는 YouTube의 사전 서면 허가에 따른 경우로 제한됩니다.
>
> 따라서 사람이 화면에서 수동으로 한두 문장을 복사한 상황과, 자동화 또는 반복적인 방식으로 자막을 수집해 앱 데이터베이스에 넣는 상황은 구분해야 합니다. 후자는 API 사용 여부와 별개로 **스크래핑 금지 및 저작권·계약 위반 위험**이 훨씬 커집니다.
> 또한 자막은 영상과 분리된 순수한 텍스트처럼 보이더라도, 영상의 대사·내레이션·각본을 그대로 담은 것이라면 영상에 부수되는 표현물 또는 독립적인 저작물로 취급될 가능성이 있습니다.
>
> **재작성하면 허용되나요?**
>
> **재작성은 원문 복제보다는 위험을 낮출 수 있지만, 그 자체로 약관상 허용을 의미하지는 않습니다.**
>
> | 사용 방식 | 위험 평가 |
> |---|---|
> | 자막 원문을 그대로 앱에 게시 | 매우 높음. 복제·배포 및 저작권 문제가 직접 발생할 수 있음 |
> | 문장 순서·단어만 조금 바꾼 패러프레이즈 | 여전히 높음. 원문의 표현과 구조를 실질적으로 재현하면 2차적 이용으로 볼 수 있음 |
> | 핵심 사실만 추출해 독자적인 설명·분석·퀴즈로 작성 | 상대적으로 낮음. 다만 영상의 독창적 표현·대사·구성을 재현하지 않아야 함 |
> | 짧은 인용과 출처·영상 링크를 함께 제공 | 경우에 따라 가능하지만, 인용 요건과 분량·목적을 충족해야 하며 YouTube 약관 문제가 별도로 남음 |
> | 여러 영상의 자막을 수집해 검색·요약 데이터베이스로 제공 | 높음. 스크래핑, 저장, 데이터 재구성 및 대체 서비스 문제까지 발생 가능 |
>
> 특히 **재작성 결과가 원문의 표현을 거의 그대로 보존하거나**, 원문을 읽지 않으면 만들기 어려운 상세한 대사·장면 순서·서술 구조를 유지한다면 단순한 아이디어 이용이 아니라 보호되는 표현의 변형으로 평가될 가능성이 있습니다. 반대로 영상에서 얻은 일반적 사실이나 주제를 바탕으로 독립적인 글을 새로 구성하고, 자막 특유의 문장·대사·배열을 재현하지 않는다면 저작권 측면의 위험은 낮아질 수 있습니다.
> 다만 YouTube API 개발자 정책은 API Data에 관해 별도로 권리 제한을 둡니다. 정책은 허용된 권리 외에는 API Data에 추가 권리나 허가가 없다고 하며, API 클라이언트가 API Data를 사용해 새로운 또는 파생된 데이터·지표를 만들지 못하도록 규정합니다.
>
> **실무적으로 안전한 기준**
> 1. YouTube 화면에서 자막을 대량 수집하거나 자동 저장하지 않습니다.
> 2. 자막 원문과 유사한 문장, 대사, 문장 순서, 장면별 서술을 게시하지 않습니다.
> 3. 앱의 핵심 콘텐츠를 자막 복제·요약본에 의존하지 않고, 직접 조사·작성한 독립 콘텐츠로 구성합니다.
> 4. 특정 영상의 내용을 사용해야 한다면 영상 ID, 제목, 채널, 링크와 출처를 명확히 표시합니다.
> 5. 영상의 대사나 스크립트를 이용하려면 업로더 또는 실제 저작권자로부터 별도 허락을 받습니다.
> 6. YouTube API를 이용하는 앱이라면 API 약관, 개발자 정책, 데이터 보관기간·삭제요건을 함께 검토합니다.
>
> 또한 약관 자체가 "현지 언어 번역본은 참고용이며 영어 버전만 법적 구속력이 있다"고 규정하므로, 한국어 번역과 영문 사이에 차이가 있으면 영문이 우선합니다.
> 따라서 질문의 사례에 대한 실무적 답은 **"자막 텍스트에도 위험이 적용될 수 있고, 단순히 재작성했다는 이유만으로 허용된다고 볼 수 없다"**입니다. 특히 자동 수집·저장·앱 게시라면 §16.3만이 아니라 스크래핑 금지, 제3자 권리, 저작권법까지 함께 검토해야 하므로, 상업 앱의 핵심 기능으로 구현하기 전에는 변호사 또는 저작권 전문기관의 검토를 받는 것이 좋습니다.

### 답 ③ ⭐ 창업자 본인의 정리 — **이걸 우리 판정으로 삼는다**

> 확인한 결과를 정리하면, **"긁어오기"는 안 되고, "레시피 정보만 독자적으로 다시 쓰기 + 공식 임베드 플레이어로 영상 표시"는 가능**한 구조입니다. 핵심은 문체가 아니라 **수집 방법**입니다.
>
> **1. 스크립트 긁어오기 자체가 문제**
> - 개발자 정책 III.E.6: You and your API Clients must not, and must not encourage, enable, or require others to, directly or indirectly, scrape YouTube Applications or Google Applications, or obtain scraped YouTube data or content.
> - III.I.14: use any technology other than YouTube API Services to access or retrieve API Data 도 금지. 즉 youtube-transcript 류 라이브러리나 페이지 파싱은 모두 여기에 걸립니다.
> - 정식 API의 자막 다운로드(captions.download)는 This method is requires the user to have permission to edit the video. — **영상 소유자만** 가능하므로, 남의 레시피 영상 자막을 API로 합법적으로 받을 길이 없습니다.
>
> 결론: 자동이든 수동 반복이든 타인 영상의 스크립트를 앱 DB에 넣는 파이프라인은 약관상 성립하지 않습니다. 문체를 바꿔도 "scraped YouTube data를 obtain"한 사실은 그대로 남습니다.
>
> **2. 저작권 측면 (한국법)**
> 레시피의 재료·분량·조리 순서 자체는 아이디어/사실이라 저작권 보호 대상이 아닙니다. 다만 영상 속 내레이션 표현, 설명 순서, 비유 등은 표현물이라 문장만 바꾼 패러프레이즈는 2차적 저작물 문제가 남을 수 있습니다. **스크립트 없이 영상을 보고 레시피 정보만 독자적으로 정리**하면 저작권 위험은 낮습니다.
>
> **3. 영상 함께 올리기**
> 공식 iframe 임베드는 허용됩니다. 단 III.F.2 브랜딩(출처 표시), III.E.4.j Made for Kids 확인, III.G.1.d(YouTube 데이터 페이지에 광고를 팔려면 독립 가치가 있는 자체 콘텐츠가 같은 화면에 있어야 함) 정도를 지키면 됩니다. 한끼처럼 자체 레시피 텍스트가 주 콘텐츠면 이 조건은 충족됩니다.
>
> **실무 정리**
>
> | 방식 | 판단 |
> |---|---|
> | 스크립트 크롤링 → LLM 재작성 → 게시 | 불가 (스크래핑 금지, 저작권 위험) |
> | 영상 보고 재료·단계만 직접 작성 + 임베드 + 출처 표기 | 가능 |
> | 채널 주인에게 허락받고 스크립트 사용 | 가능 (서면 허락 권장) |
>
> 저는 변호사가 아니니, 상용 앱 핵심 기능으로 굳히기 전에는 한국저작권위원회 상담 등으로 한 번 확인하시길 권합니다.

> ⛔⛔ 위 6️⃣ 에 「아직 모르는 것」으로 남겨둔 것을 **닫는다.** 답은 우리가 바라던 쪽이 아니었다.

### 무엇이 사실인가 (AI 둘이 «따로» 원문을 읽고 «같은» 답을 냈다)

- 📄 **조항 위치** = 약관 본문이 아니라 부속문서 **「Developer Policies」** III.E.4.j
  (페이지 표기로는 III.E.4.10 · 최종 갱신 2026-06-24)
- 📄 **원문** = *"API Clients must look up the Made For Kids status of **each YouTube video that it embeds
  on its site or app**"* → MFK 인 영상은 **추적을 끄고** COPPA·GDPR 을 지켜야 한다
- ⭐⭐ **임베드만 써도 해당된다** — 근거 셋
  ⑴ 유튜브 공식 도움말 = *"apply to **all access and use of the YouTube embedded player**"*
  ⑵ Required Minimum Functionality = *"API Clients that use the YouTube embedded player (**including** the IFrame Player API)"*
     → 임베드 플레이어가 상위, IFrame API 가 그 하나다. 그냥 `/embed/ID` 도 포함
  ⑶ 2020년 이 조항 도입 때 변경이력이 *"any YouTube embedded players"* 라고 못 박았다
- 🔎 **조회 방법** = Data API `videos.list` · `part=id,status` · 응답의 `status.madeForKids`
  🔢 무료 쿼터 10,000/일 ＝ 약 5,000편. 우리는 **주 1편**이라 넉넉하다

### ⛔ 그래서 우리가 틀렸던 것

이 문서와 `유튜브레시피-받는서식` 에 *"API 안 쓰니 상관없다"* 는 전제가 깔려 있었다. **아니었다.**
🔢 실측(2026-09-04) = `embed.js:15` 이 `https://www.youtube.com/embed/{id}?playsinline=1` 를 쓰고,
   **MFK 조회는 어디에도 없다.** 이미 나간 SNS 레시피 3편이 그 상태다.

### ✅ 창업자 확정 = **ⓐ 조회를 붙인다** (2026-09-04 *"ⓐ로 가자"*)

| | |
|---|---|
| **언제 조회하나** | 영상을 «넣을 때» 한 번. 유저가 볼 때마다가 아니다 |
| **누가** | **클로드가 직접** — 실측으로 `www.googleapis.com` 이 열려 있음을 확인했다(400 응답) |
| **어디에 남기나** | 레시피 데이터에 `mfk: true/false` (채널명을 손으로 적는 것과 같은 결) |
| **분기** | `mfk: true` → 추적 없는 임베드 · `false` → 지금 그대로 |
| **잊지 않는 법** | ⭐**게이트** — `sourceUrl` 이 있는데 `mfk` 가 없으면 **배포를 막는다** |

⏳ **창업자 몫 = YouTube Data API 키 발급 한 번**(구글 클라우드 콘솔 · 무료).
   ⛔ 키는 **저장소에 안 넣는다** — 대화로 받아 조회에만 쓰고, 결과만 코드에 박는다. 앱엔 안 들어간다.

### ⚠️ 이것과 «별개»인 것 — 앱 등급 3세 이상

III.J(Child-Directed API Clients)는 **스토어 등급이 아니라 «법률상 아동을 겨냥했나»**가 잣대다.
3세 이상 등급이라고 자동으로 해당되지 않는다. ⛔다만 이건 **법률 판단이라 AI 둘 다 단정을 피했다.**
⏳ 한국저작권위원회 상담(6️⃣ 에 남은 것)과 함께 **창업자 판정 사항**으로 남는다.
