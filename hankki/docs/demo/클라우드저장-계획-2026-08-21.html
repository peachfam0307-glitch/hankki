제일 큰 것

① 흔히 쓰는 로그인 방식이 우리 환경에선 깨진다

Firebase 로그인에는 두 방식이 있는데, 널리 쓰이는 리다이렉트 방식은 「서드파티 쿠키」에 기대. 그런데 크롬·사파리·파이어폭스가 그걸 막았어.

Firebase 공식 — “이 방식은 서드파티 저장소 접근을 막는 브라우저에서 동작하지 않는다. 2024-06-24부터 크롬에서도 권장 옵션을 적용해야 한다.”

우리 앱은 GitHub Pages에 있어서 정면으로 걸려. 그냥 만들었으면 네 폰에서 로그인이 안 되는 걸 다 만든 뒤에 알았을 거야.

✅ 길이 둘 있고, 하나는 이미 통과한 길이야
ⓐ 팝업 방식 — 공식 1순위. 쿠키를 안 써. 코드가 제일 짧아. ⛔단 TWA(우리 앱) 안에서 도는지는 모른다
ⓑ 8/19에 우리가 통과시킨 그 흐름 — 구글에서 열쇠를 직접 받아 Firebase에 넘긴다. 이미 네 폰에서 실물로 됐던 길이라 확실해
👉 ⓐ를 폰에서 한 번 눌러보고, 안 되면 ⓑ. 막다른 길이 아니야.
데이터 모양

② 한 덩어리로 올리면 안 된다 — 문서 하나가 1MB까지

Firestore는 문서 하나에 최대 1MB야. 레시피 한 편이 약 1.46KB니까 글자만 쳐도 685편이면 한계고, 꾸민 것·일기까지 한 덩어리면 훨씬 빨리 차.

→ 레시피 한 편 = 문서 한 개로 쪼갠다. 아래 그림 참고.

비용

③ 무료 한도 = 저장 1GB · 읽기 5만/일 · 쓰기 2만/일

넉넉해. 다만 로그인할 때마다 전부 읽으면 레시피 200편 = 200번 읽기야.

→ 「지난번 이후 바뀐 것만」 읽게 짠다. 그러면 평소엔 몇 번으로 떨어져.

우리 문서가 갈렸던 자리

④ OAuth 동의 화면을 「게시」해야 한다

테스트 모드로 두면무슨 일
유저 수100명이 하드캡 — 넘으면 로그인 자체가 안 된다
로그인 유지7일 뒤 만료 — 일주일마다 다시 로그인

✅ 검증(2~6주)은 안 걸려 — 우리는 로그인만 쓰니까 기본 권한뿐이고, 기본 권한만 쓰는 앱은 검증 없이 게시돼.

⚠️ 우리 문서엔 「게시 누르지 마」라고 적혀 있었는데 그건 8/19 «실험» 때 얘기였어. 모순이 아니라 시점이 달랐던 것 — 실험은 테스트, 서비스는 게시. 문서 고쳐뒀어.

데이터를 어떻게 두나

쪼개되, 내려받아 합치면 백업 파일이 그대로 나오게. 그게 갈아타기 보험 ②야.

users/{구글 고유번호} ← 열쇠 = 구글 sub (보험 ①) ├ meta 프로필 · 폴더 · 장보기 · 냉장고 … ├ recipes/{id} 레시피 한 편 = 문서 한 개 └ diary/{id} 일기 한 장 = 문서 한 개

⭐ 문서 하나하나가 백업 파일 속 모양 그대로라, 나중에 🅱(클라우드플레어)로 옮겨도 내려받아 그대로 올리면 끝이야.

⛔ 사진은 안 올려 — 네가 확정한 「글자부터」 그대로. 사진은 폰이랑 백업 파일에 그대로 남아.
