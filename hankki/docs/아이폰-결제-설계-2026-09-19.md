# 🍎💳 아이폰 결제(인앱 구매) 설계 — 1판 (2026-09-19 · 아이폰 세션)

📮 창업자 = *"결제 넣기 켜려는데 그것도 설계해야해."* · *"중요한 것들이니까 제대로 설계해줘."*
🔗 짝 문서 = `docs/결제-여는-순서-2026-09-19.md`(전체 순서 · 행정 · 값) · `hankki/src/billing.js`(구글 길 · Digital Goods API) · `hold/결제서버-0819`(`ocr-proxy/worker.js` 의 `/billing/sync` 원장 · 구글 검증). **값(990원·20개)·파는 자리·행정은 그 문서를 따른다.** 여기는 «아이폰에서 어떻게 사고, 어떻게 확인하고, 어떻게 넣어주나»만.

## 0. 실물 (2026-09-19 밤에 연 것)
- 지금 결제 코드 = **구글 전용**. `billing.js` 는 `window.getDigitalGoodsService('https://play.google.com/billing')` 이 없으면 조용히 `null` → 아이폰에선 **결제 단추가 아예 안 그려진다**(`canBuy()` false). 앱은 안 깨진다 — 다만 «못 판다».
- 상품 = 꾸미기 팩 5종(영구 · `deco_*`) ＋ 글자인식 20장(소모성 · `ocr_pack_20`). 창업자 새 안 = **레시피열쇠 20개 990원**(소모성).
- 서버 = hold 의 `/billing/sync`: 앱이 «가진 구매»를 통째로 보내면 → 구글에 진짜냐 묻고(androidpublisher) → **uid 원장**에 적고 → 다 쓴 소모성은 consume. **여기에 아이폰 칸을 «덧붙이는» 구조가 맞다**(원장·열쇠 지급 길은 하나로).
- 열쇠 잔액 = 서버가 준다(`ocr.js` `열쇠받기`/`열쇠새로고침` · 화면 `useKeyLeft.js`). 즉 **아이폰에서 사도 «넣어주는 자리»는 이미 있다** — 원장에 +20 만 적으면 화면이 따라온다.
- 아이폰 앱 플러그인 = firebase-auth · filesystem 뿐. **StoreKit 플러그인 0.**

## 1. ⛔ 애플 규칙 두 줄 (설계를 가르는 것)
1. **디지털 상품(열쇠·꾸미기 팩)은 반드시 애플 인앱 구매(StoreKit)로**. 웹 결제창·아웃링크로 팔면 심사 거절(가이드라인 3.1.1). ⛔ 구글 길(`PaymentRequest`)은 아이폰에선 애초에 없다.
2. **수수료 30% → Small Business 승인 뒤 15%** = 990원이면 손에 약 693원 → 약 841원. (짝 문서 §1-3 · 「미루면 손해」)
⚠️ 위 둘은 오늘 공식 원문을 «다시» 열진 못했다(개발자 사이트 망 차단). 1번은 짝 문서·실전기 6장에 이미 기록된 것과 같고, 2번은 짝 문서 §3 값 그대로다.

## 2. 그림 — 「사는 곳은 둘, 확인하고 넣어주는 곳은 하나」
```
[갤럭시 앱]  Digital Goods API ─ purchaseToken ─┐
                                              ├─▶ 워커 /billing/sync { platform, uid, 증거 }
[아이폰 앱]  StoreKit 2 ─ 서명된 거래(JWS) ─────┘      ├ android → 구글 API 로 확인
                                                       ├ ios     → 애플 서명 확인(또는 App Store Server API)
                                                       └ 원장(uid) ＋20 → 앱은 열쇠새로고침()
```
- **uid = 지금 로그인 uid**(Firebase). 아이폰 유저는 로그인 필수(09-07 결정)라 uid 가 늘 있다 → 폰을 바꿔도 **소모성 잔액이 따라온다**(구글 쪽 「폰 바꾸면 남은 장수 안 따라옴」 문제가 우리 원장으로 풀린다 · 두 플랫폼 공통).
- 꾸미기 팩(영구) = 애플이 Apple ID 로 «복원»을 스스로 해 준다 → 우리 원장에도 적되, 복원 단추는 애플 API 를 부른다(심사 요구 = **「구매 복원」 단추가 있어야 한다**).

## 3. 앱 쪽 (아이폰)
| 층 | 무엇 |
|---|---|
| 플러그인 | Capacitor 용 StoreKit 플러그인 하나(후보 = `@capacitor-community/in-app-purchases` 또는 RevenueCat `purchases-capacitor`). ⭐추천 = **직접 StoreKit 2 를 감싼 얇은 플러그인**(우리 `ShareIntakePlugin.swift` 처럼 Swift 파일 하나) — 상품 3~6개에 RevenueCat 가입·월정액·SDK 무게는 과하다. 필요한 함수 넷 = `상품(ids)` · `사기(id)` · `복원()` · `가진거래()` |
| `billing.js` | 지금 «구글만» 보는 `service()` 를 **플랫폼 갈래**로: Capacitor iOS 면 StoreKit 플러그인, 아니면 Digital Goods. 위 함수 이름(`canBuy`·`details`·`buy`·`purchases`·`consume`)은 **그대로 두고 속만 갈라** — `PackBuySheet.jsx` 등 화면은 안 고친다 |
| 상품 ID | App Store Connect 에 **구글과 같은 글자**로 등록(`deco_halloween` · `ocr_pack_20` · 새 `keys_20`). 한 벌만 관리 |
| 소모성 | StoreKit 2 는 산 뒤 `finish()` 를 불러야 끝난다 → **워커가 원장에 적은 «뒤»에** finish(먼저 finish 하고 서버가 죽으면 돈만 나가고 열쇠 못 받는 사고) |
| 복원 | 설정·구매 시트에 「구매 복원」 단추 → `복원()` → 가진 거래를 `/billing/sync` 로 |
| 실패 | 유저가 닫음 = «안 삼»(문구 없음 · 구글과 같은 원칙) · 결제됐는데 서버가 안 됨 = 거래를 finish 안 하고 두면 **다음 켤 때 StoreKit 이 다시 준다** → 그때 sync → 안전 |

## 4. 서버 쪽 (워커 · hold 판에 덧붙임)
- `/billing/sync` 에 `platform: 'ios'` 갈래. 증거 = StoreKit 2 의 **서명된 거래(JWS)**. 확인 = ⓐ JWS 서명을 애플 루트 인증서로 검증(오프라인 · 무료 · 빠름) 또는 ⓑ App Store Server API 로 거래 ID 조회(App Store Connect 의 **In-App Purchase 키** 필요 · 이미 있는 배포용 API 키와 «다른» 키). ⭐1판 = ⓐ, 환불·문제 거래 조회는 ⓑ 로 2판.
- 원장 = 구글과 **같은 표**에 `platform` 칸만. 같은 거래 ID 가 두 번 오면 +20 을 두 번 하지 않는다(⛔멱등 · 재현판으로 박는다).
- 환불 = 애플 **App Store Server Notifications V2**(REFUND) 를 워커 주소로 받아 원장에서 −20(잔액이 음수면 0에 멈춤 · 이미 쓴 건 회수 안 함). 2판.
- ⛔ 비밀(In-App Purchase 키 .p8 · 발급자 ID) = 워커 secret 에만.

## 5. 행정 (창업자 몫 · 짝 문서 §1 그대로) — 순서가 결제를 막는다
1. **유료 앱 계약 서명 ＋ 은행 ＋ W-8BEN** → `Pending validation` 기다림 → **활성화 뒤에만 상품 등록이 열린다**
2. **Small Business 신청**(계약 뒤 바로)
3. App Store Connect → 앱 → **인앱 구매** → 상품 만들기(소모성 `keys_20` 990원 · 심사용 스크린샷 1장 필요 · 현지화 이름/설명)
4. **Sandbox 테스터** 계정 하나(Users and Access → Sandbox) → 딸 폰에 넣어 시험(⛔실결제 안 나감) — 계정 정보는 대화·저장소에 안 적는다
5. **첫 인앱 상품은 «앱 버전과 함께» 심사에 낸다**(버전 페이지 아래 「인앱 구매」 칸에 붙임). 이후 상품은 따로 낼 수 있다

## 6. 순서 (아이폰 몫) — 갤럭시 결제 서버가 «배포된 뒤» 시작
1. 갤럭시가 hold 결제서버를 지금 코드에 붙여 배포(짝 문서 §2-1) — 원장·`/billing/sync` 가 실제로 돌아야 아이폰이 붙을 자리가 생긴다.
2. 나 = ① StoreKit Swift 플러그인 ② `billing.js` 플랫폼 갈래 ③ 워커 ios 갈래(JWS 검증 · 멱등) ④ 재현판(두 번 sync 해도 +20 한 번 · finish 는 원장 뒤) → **hold 갈래**에.
3. 창업자 = 계약·상품·Sandbox 테스터(5절).
4. 새 빌드(N판) → 딸 폰 Sandbox 로 사기·복원·앱 지웠다 깔기 3가지 실측 → 1.0.x 제출 때 인앱 상품 «함께» 첨부.
5. 갤럭시 웹은 아이폰 승인 날 같이 연다(09-18 규칙).

## 7. 세 각도 검토 (설계 관문)
- 👩 사람: 열쇠 0인 아이폰 유저가 「20개 990원」을 누른다 → Face ID 창 → 결제됐는데 화면 잔액이 그대로면 「돈 나갔는데 안 왔다」 → **결제 직후 시트에 「열쇠를 넣는 중…」 → 원장 확인 → 「+20」 애니메이션까지 한 흐름**, 실패 시 「다음에 앱을 켜면 자동으로 들어와요」 문구(finish 안 했으니 진짜 들어온다).
- 💥 사고: ⓐ 서버가 +20 적은 뒤 앱이 죽어 finish 를 못 함 → 다음 켤 때 같은 거래가 또 온다 → **멱등**이라 +20 안 겹침 → finish. ⓑ 탈옥폰이 가짜 JWS 를 보냄 → 서명 검증에서 걸러짐(구글 쪽 「검증 안 붙였다」 빚과 달리 아이폰은 1판부터 검증). ⓒ 창업자가 상품 ID 를 `keys20` 으로 등록 → 앱은 `keys_20` → 상품이 안 뜬다 → **상품 ID 를 `billing.js` 한 곳에서만 쓰고, 등록 캡처와 대조하는 검사판**.
- 📈 규모: 91명 중 아이폰 몫이 작다(iOS 로그인 하루 1명) → 첫 달 매출 기대 ≈ 0. 그래서 **RevenueCat 같은 유료·중량 SDK 를 안 쓰고** 얇게 간다. 1만 명이 되면 환불 알림·Server API(2판)를 붙인다. 워커 호출 = 구매 때 1번 · 켤 때 sync 1번 → 무료 한도 안.
- 잃던 것(지금) = 아이폰 유저는 «돈을 내고 싶어도 못 낸다» · 아이폰 심사에 「구매 복원 없음」 위험. 잃을 것(고친 뒤) = 애플 수수료 30/15% · 행정 대기(Pending validation) · 유지할 플러그인 하나.
