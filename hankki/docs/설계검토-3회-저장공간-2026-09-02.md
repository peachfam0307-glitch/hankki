### ⛔⛔ 3차가 잡은 «설계 결함»
**「켤 때 사진을 전부 읽어 메모리에 얹는다」가 절대원칙 32 ④를 그대로 어긴다** — 데이터 수에 «선형»이다.
　유저 수엔 안 늘지만 **한 사람이 오래 쓰면** 켜는 시간과 메모리가 계속 는다. **결국 같은 반복이다.**

⛔ 「표지 사진만 읽자」로도 **부족하다** — 오래 쓴 사람은 레시피마다 완성 사진을 표지로 삼아 **500장**이 될 수 있다.

### ✅ 3차가 낳은 «설계 변경» — 이게 제일 크다
**「화면에 보이는 것만 꺼낸다」**
· 🔎 확인 = **표지를 그리는 곳은 `Thumb.jsx` «한 곳»뿐**(화면 열여섯이 전부 거친다 · 예외는 편집 미리보기 하나)
· → `Thumb` 이 **자기가 그릴 때** 사진을 꺼낸다 → **켤 때 드는 값 0** · 메모리는 **화면에 뜬 것만**
· → 레시피가 1만 편이어도 **켜는 시간·메모리가 안 는다** ＝ 절대원칙 32 통과
· ⚠️ 일괄로 «전부» 필요한 곳 둘은 따로 챙긴다 — **백업 만들기**(`backupData.js:21`) · **클라우드 카드 올리기**(`cloud.js:191`, ⛔이 함수는 «동기»라 미리 받아둬야 한다)

### 🌍 유저 수
· 폰 안 저장은 **1만이든 100만이든 값이 같다** ✅

## 2️⃣차 · 사고 — (남의 눈으로 검토 중 · 결과가 오면 여기에 얹는다)

### 🔬 3차 보강 — 전제를 실물로 확인했더니 «한 번 더» 틀렸다
🛠 `scripts/_probe-표지몇개-0902.mjs`
| 잰 것 | 값 |
|---|---|
| 저장된 레시피 | 62 |
| **한 번에 그려진 칸** | **62 (전부)** |
| 화면에 실제로 보이는 칸 | **6** |

⛔ **목록이 전부를 그린다**(가상 스크롤 없음) → 「`Thumb` 이 자기 사진을 꺼낸다」만으로는
　 **62장(나중엔 1000장)을 한꺼번에 읽는다.** 선형 문제가 그대로 남는다.
✅ **그래서 「그릴 때」가 아니라 «화면에 들어올 때»** 꺼낸다(`IntersectionObserver`).
　 → 읽는 양이 **화면에 뜬 6~12장**으로 묶인다. 레시피가 1만 편이어도 같다. ⭐**절대원칙 32 ④ 통과.**
📌 **이 확인을 안 했으면 「고쳤다」고 말하고 같은 벽에 다시 갔다.**
**남의 눈으로 검토했다**(적대적 검토 · `src/` 전수). ⭐ 제일 큰 셋은 **내가 다시 확인했다**(규칙 29).

### 🔥 제일 위험한 셋 — 전부 «확인됨»

| | 무엇 | 확인 방법 | 나쁨 |
|---|---|---|---|
| **㉠** | **`importAll` × IndexedDB = 「복원」이 곧 「사진 삭제」** — 백업/클라우드 복원은 **동기·통째 교체**라 IDB를 모른다. 사진 든 판이 state 로 들어오고 persist 가 벗겨서 localStorage 에 쓴다 → **IDB엔 한 장도 안 들어간다** → 다음에 켜면 사진이 전부 사라진다 | `store.jsx:1039~1053` 을 열어 확인 | 🔴🔴 |
| **㉡** | **캡처 수명(ⓐ4)이 «이미 꽉 찬 폰»에는 효과가 0** — `INBOX_V 2`(오늘 아침 판)가 이미 전부 `sorted` 로 바꿔놔서 **그 편들은 졸업 지점을 다시 안 지나간다.** 즉 **잃기만 하고 안 비운다** | 코드 논리로 확인 | 🔴🔴 |
| **㉢** | **계기판(ⓒ)이 «틀린 벽»을 잰다** — `navigator.storage.estimate()` 는 **localStorage 를 안 센다** | 🛠 `_probe-계기판-0902` 실측 = **1MB 넣어도 0KB** | 🔴 |

### ＋ 2차가 찾은 다른 구멍 (골라 적는다)
| 무엇 | 나쁨 |
|---|---|
| **`importAll` 이 마이그레이션 도장 «다섯»을 안 넘긴다**(`politeV·qtyOnlyV·inboxV·coverV·sampleGone`) → 복원하면 전부 다시 돈다. ⭐**내 설계 탓이 아니라 «지금 있는» 버그** | 🔴 |
| persist 가 **모든 dispatch마다** state 전체를 쓴다 → 사진을 IDB에 넣는 코드도 그중 하나 → **하이드레이션 순간 사진이 도로 localStorage 로 간다.** 직렬화 자체를 갈아야 한다 | 🔴 |
| **IDB commit «전»에 localStorage 에서 빼면 반쪽 저장** — 순서를 반드시 「IDB 먼저 → 그다음 뺀다」 | 🔴 |
| 「저장됐어요」가 **localStorage 성공만** 본다 → IDB 실패해도 «성공»이라 말한다(오늘 사고의 재발) | 🔴 |
| SHRINK 루프가 `useEffect(…, [])` 라 **첫 렌더 클로저** → 하이드레이션 전 `image:null` 만 봐서 **영영 안 돈다** | 🔴 |
| **레시피를 지워도 IDB 사진이 남는다** — `remove·clear·reset` 셋 다. ⛔`delete-account.html` 이 「앱에서 직접 삭제」를 약속하고 있어 **신고와 어긋난다** | 🟠 |
| ⓐ4 가 **어제 약속을 깬다** — `COVER_V` 가 `thumb` 도장을 지워서 예외(`thumb==='photo'`)를 **빠져나가 삭제**된다 | 🔴 |
| `다읽었나()` 는 **줄 수만 센다** — 엉터리 OCR도 졸업 → 대조할 사진이 사라진다 | 🔴 |
| `rawText` 는 **8/22 이후 ＋ 4000자 이하**일 때만 있다 → 「원문은 남는다」가 **늘 참이 아니다** | 🔴 |
| 두 탭 = IDB `blocked` 처리가 없으면 새 탭이 **평생 사진을 못 본다** · `storage` 이벤트 리스너 **0개** | 🟠 |
| 사진은 `recipe.image` 말고도 **다섯 군데** 더 있다(decor·일기·속지·일기 decor·아바타) → `cloud.js` 처럼 **「`data:` 로 시작하나」로 훑어야** 한다 | 🔴 |
| 새 서비스워커가 **예고 없이 `location.reload()`** — 이사 중에도 터진다 | 🔴 |
| ⓐ1(카드 예외)은 **이미 넣었다**(오늘 낮) — 설계 문서가 낡았다 | 🟡 |

# ✅ 세 번을 돌고 나서 — 설계가 이렇게 바뀐다 (⭐여기가 현행이다)

## ⛔ 접는 것 — **ⓐ4「캡처 수명 = 임시보관함까지」**
창업자가 오늘 아침 고른 것이지만, 세 번 흔드니 **근거가 무너졌다**:
· ㉡ **이미 꽉 찬 폰엔 효과 0** — 잃기만 하고 «안 비운다»
· 어제 약속(`COVER_V`) 과 **모순** · `다읽었나()` 는 **맞게 읽혔는지 안 본다** · `rawText` 가 **없을 수 있다**
· **되돌릴 수 없다** · 무료 유저 생명줄을 **조건부로** 만든다(CLAUDE.md 가 ⛔로 못 박은 것)

⭐⭐ **그리고 벽을 없애면 «지울 이유 자체»가 사라진다.**
　 창업자가 「임시보관함까지만」을 고른 건 **5MB 안에서 버티려고**였다. 벽이 없어지면 그 대가를 치를 이유가 없다.
　 📌 **이건 창업자에게 판정을 «되돌려 드리는» 게 아니라, 판정이 «필요 없어졌다»는 보고다.**
