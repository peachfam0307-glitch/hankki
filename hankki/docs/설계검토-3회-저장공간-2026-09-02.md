# 🔁 설계 검토 세 번 — 저장 공간 (2026-09-02 · 절대원칙 33)

> 📮 창업자 = *"절대원칙 여러가지 상황을 시뮬레이션해서 **총 3번 다각도로 검토한다.** 그 다음 보고해줘"*

**검토 대상** = ⓐ버그 넷(카드 예외·옛 카드 도장·임시저장 사진 빼기·캡처 수명) ／ ⓑ사진만 IndexedDB ／ ⓒ폰 계기판＋경보

## 1️⃣차 · 사람 — 유저를 «세워놓고» 따라갔다

| 누구 | 어디서 깨지나 | 얼마나 |
|---|---|---|
| **갓 깐 사람** | 캡처가 «졸업할 때 조용히» 사라진다. 유저는 *"저장했으니 사진도 있겠지"* 라고 안다 | 🔴 |
| **오래 쓴 사람(창업자·257편)** | 업데이트하면 마이그레이션 **넷이 한꺼번에** 돈다 ＋ **이미 꽉 찬 상태**에서 돈다 | 🔴 |
| **무료 유저(열쇠 0)** | 「보면서 쓰기」가 생명줄인데… ✅ **예외 ②가 지켜준다** — 기본 인식은 대개 반쪽만 읽어 **임시보관함에 남는다** | 🟢 지켜짐 |
| **폰 바꾼 사람** | 백업엔 사진이 있다 → 복원 뒤 수십 장을 한꺼번에 IDB 로 쓴다 | 🟠 |
| **레꾸를 많이 하는 사람** | 카드 표지 0.5~0.9MB × 여러 편 → IDB 로 가도 **백업 파일이 20MB** 가 된다(공유 실패) | 🟠 |

### 🔧 1차가 낳은 고칠 것 셋
| | 무엇 | 왜 |
|---|---|---|
| **1-A** | **캡처를 지울 땐 «말한다»** — 조용히 지우지 않는다 | 유저는 사진이 남아 있다고 안다. 오늘 사고가 «조용해서» 나빴다 |
| **1-B** | **마이그레이션 «순서»를 못 박는다** = ①캡처 비우기(작아짐) → ②카드 도장 → ③IDB 이사 | 꽉 찬 상태에선 **먼저 줄여야** 그다음 쓰기가 성공한다 |
| **1-C** | **한 번에 하나씩** 돌린다 | 넷이 동시에 돌면 첫 실행이 멎는다 |

## 3️⃣차 · 규모·시간 — 유저 수 × 데이터 수 × 시간

### 🔢 실측 (`_probe-idb-0902`)
| 사진 | 켤 때 읽기 | 메모리 |
|---|---|---|
| 100장 | 111ms | 13MB |
| **500장** | **869ms** | **65MB** |
| 1000장(1년 뒤) | ≈1.7초 | ≈130MB |

### ⛔⛔ 3차가 잡은 «설계 결함»
**「켤 때 사진을 전부 읽어 메모리에 얹는다」가 절대원칙 32 ④를 그대로 어긴다** — 데이터 수에 «선형»이다.
　유저 수엔 안 늘지만 **한 사람이 오래 쓰면** 켜는 시간과 메모리가 계속 는다. **결국 같은 반복이다.**

⛔ 「표지 사진만 읽자」로도 **부족하다** — 오래 쓴 사람은 레시피마다 완성 사진을 표지로 삼아 **500장**이 될 수 있다.

### ✅ 3차가 낳은 «설계 변경» — 이게 제일 크다
**「화면에 보이는 것만 꺼낸다」**
· 🔎 확인 = **표지를 그리는 곳은 `Thumb.jsx` «한 곳»뿐**(화면 열여섯이 전부 거친다 · 예외는 편집 미리보기 하나)
· → `Thumb` 이 **자기가 그릴 때** 사진을 꺼낸다 → **켤 때 드는 값 0** · 메모리는 **화면에 뜬 것만**
· → 레시피가 1만 편이어도 **켜는 시간·메모리가 안 는다** ＝ 절대원칙 32 통과
· ⚠️ 일괄로 «전부» 필요한 곳 둘은 따로 챙긴다 — **백업 만들기**(`backupData.js:21`) · **클라우드 카드 올리기**(`cloud.js:191`, ⛔이 함수는 «동기»라 미리 받아둬야 한다)
